## 2. Найденные несоответствия документации и кода (исправлены)

1. `docs/architecture.md` указывал таблицу `otp`, тогда как в БД таблица `reset_codes`. Исправлены схема в диаграмме и описание.
2. `docs/architecture.md` упоминал guard-функции `requireAuth` / `requireClassroomMember`, которых нет; реальные имена — `createAuthenticateUser`, `createLoadClassroomMember`, `requireClassroomRole`. Документ обновлён.
3. `docs/domain-model.md` обещал `CHECK`-ограничение на роль участника, а его не было. Ограничение добавлено в схему новых БД, а для старых БД документ честно указывает на валидацию на уровне API.
4. `docs/deployment.md` содержал фрагмент `docker-compose.yml`, отличавшийся от реального файла (`PORT` в `environment`, отсутствие `init`, `stop_grace_period`, ротации логов, `LISTEN_HOST`). Фрагмент приведён в точное соответствие.
5. README не описывал требования к DNS/портам 80–443, неинтерактивные флаги установщика, обновление, резервное копирование и диагностику. Добавлены разделы.
6. ADR-5 формулировал «default `BIND_HOST=127.0.0.1`», хотя это делает установщик только для HTTPS-профиля. Формулировка исправлена, добавлены ADR-6…ADR-8.
7. README/архитектура не упоминали `TRUST_PROXY`, HSTS, `LISTEN_HOST`, `RATE_LIMIT_*`. Документация и `.env.example` дополнены.

## 3. Найденные и исправленные баги/риски

### 3.1 Критично для школьной эксплуатации: rate limit по IP блокировал весь класс
**Проблема.** Логин, регистрация, сброс пароля и вступление по коду ограничивались только по IP. Школа/класс обычно выходит через один NAT: 20 логинов за 15 минут на весь класс — ученики получали `429`.

**Исправление.**
* логин — ключ `IP + username`, 20/15 мин (брутфорс одного аккаунта по-прежнему ограничен);
* сброс пароля — `IP + email` 5/15 мин + общий анти-спам `100/IP/15 мин`;
* подтверждение кода — `IP + email` 15/15 мин;
* вступление по коду — `IP + user_id` 25/15 мин;
* регистрация — 50/час на IP; все значения настраиваются через `RATE_LIMIT_*`.
Добавлен регрессионный тест: 30 разных учеников за одним IP не блокируются, а 25 попыток по одному логину — блокируются.

### 3.2 Критично для Docker: `BIND_HOST` нельзя использовать как адрес прослушивания внутри контейнера
**Проблема.** При HTTPS-профиле установщик ставит `BIND_HOST=127.0.0.1`, чтобы закрыть порт 3000. Если бы Node внутри контейнера слушал `127.0.0.1`, опубликованный порт Docker не смог бы достучаться до приложения (Docker проксирует на bridge-интерфейс контейнера).

**Исправление.** Разделены переменные:
* `BIND_HOST` — только интерфейс публикации порта в `docker-compose.yml`;
* `LISTEN_HOST` — адрес прослушивания Node (в Docker всегда `0.0.0.0`, зафиксирован в `environment` compose);
* `TRUST_PROXY` — доверие `X-Forwarded-*`.

### 3.3 Безопасность: слепое доверие `X-Forwarded-*` при прямом доступе по IP
**Проблема.** `trust proxy = 1` всегда + чтение `X-Forwarded-Proto` позволяло при прямом доступе подменять IP (обход rate limit) и влиять на флаги cookie/HSTS.

**Исправление.** `TRUST_PROXY` (по умолчанию `1` для обратной совместимости, установщик явно ставит `0` для `IP:3000` и `1` для Nginx). При `TRUST_PROXY=0` заголовки `X-Forwarded-*` игнорируются полностью, включая `Secure`-cookie и HSTS. Добавлен тест на оба режима.

### 3.4 HSTS отсутствовал
Добавлен `Strict-Transport-Security: max-age=15552000; includeSubDomains` **только** для HTTPS-запросов (по прямому TLS или доверенному `X-Forwarded-Proto`).

### 3.5 Некорректная обработка слишком большого тела запроса
`express.json({ limit: "256kb" })` бросал `PayloadTooLargeError`, который глобальный обработчик отдавал как `SERVER_ERROR` (500-подобный текст) и писал полный stack trace в лог. Теперь: `413 PAYLOAD_TOO_LARGE`, а клиентские `4xx` логируются одной строкой без stack trace.

### 3.6 Установщик: хрупкость и опасные краевые случаи
* **Нет проверки DNS** перед Certbot → добавлено предупреждение со сравнением A-записи и публичного IP (с возможностью продолжить; не блокирует Cloudflare/прокси).
* **Certbot без повтора** → 2 попытки с паузой 10 с и точная команда для ручного повтора.
* **Приложение могло не подняться, а установка «успешно» завершалась** → ожидание `/api/health/db` до 90 с, при неудаче — логи контейнера и код возврата 1.
* **Повторный запуск сбрасывал HTTPS-настройки** (`BIND_HOST=0.0.0.0`, `TRUST_PROXY=0`) → существующий `.env` сохраняется, добавляются только отсутствующие ключи; итоговый URL определяется по конфигу Nginx и наличию сертификата.
* **Пустые значения SMTP записывались как `SMTP_HOST=""`** → пустые значения теперь пишутся как `SMTP_HOST=`.
* **Занятый `apt` (unattended-upgrades)** → 3 повтора `apt-get update/install`.
* **Ошибки без диагностики** → `trap ERR` печатает команду, путь журнала, команды логов и `git status`; весь вывод дублируется в `/var/log/interactive-calendar-install.log`.
* **Неинтерактивность/автоматизация** → флаги `--yes`, `--dir`, `--domain`, `--email`, `--port`, `--ref`, `--no-ssl`, `--no-swap`, `--reconfigure-env`, `--smtp-*`.
* **Не проверялось, что каталог действительно содержит проект** → при непустом каталоге без `package.json`/`server.ts` установка прерывается с понятным сообщением.
* **Порт 3000 оставался в интернете при HTTPS** → после настройки Nginx публикация переводится на `127.0.0.1`, проверяется health, а затем выпускается сертификат; добавлена локальная проверка `https://<домен>/api/health` через `--resolve`.
* **Логи Docker могли забить диск VPS** → ротация `json-file` 10 МБ × 3.
* **Нет graceful stop** → `init: true`, `stop_grace_period: 15s`.

### 3.7 Пароль SMTP со знаком `$` ломался при передаче в контейнер
`install.sh` записывал значения `.env` в двойных кавычках. Docker Compose интерполирует переменные в двойных кавычках, поэтому пароль вида `p@$$w0rd#1` превращался в мусор и сброс пароля по почте не работал. Теперь значения с `$`/обратной кавычкой записываются в одинарных кавычках (Compose и `dotenv` читают их буквально); добавлен сценарий проверки.

### 3.8 Резервное копирование «на живую» могло быть несогласованным
`tar` по каталогу `data/` во время работы SQLite в WAL-режиме может захватить файл БД и `-wal` в разные моменты. Добавлен `backup.sh`: останавливает контейнер, архивирует `data/` и `.env` (права 600), затем гарантированно запускает приложение обратно, в том числе при ошибке архивации. Инструкции в README и `docs/deployment.md` обновлены.

### 3.9 Мелкие улучшения
* `CHECK (role IN ('owner','admin','member'))` для новых БД.
* Скрипты `npm run check`, `npm run test:install`, `npm run docker:build|up|down`.
* CI: Node 22/24 (типы, тесты, симуляция установщика, сборка) + отдельная job со сборкой Docker-образа и smoke-тестом (health, SPA, персистентность SQLite на volume).
* Требование bash 4+ с понятной ошибкой при запуске через `sh`; проверка доступности `/dev/tty` перед интерактивным вводом.
* Docker-образ переведён с Node 20 (EOL с апреля 2026) на Node 24 LTS; `engines.node` и CI-матрица обновлены до 22/24.
* Google Fonts больше не блокируют первую отрисовку: внешний CSS грузится неблокирующе, при недоступности Google приложение сразу использует системные шрифты.
* Исправлена потеря deep-link: при первом открытии `#/classroom/<id>/calendar` хэш перезаписывался на `#/home` до загрузки списка классов, и открывался не тот класс. Теперь синхронизация URL ждёт завершения загрузки, а недоступный класс корректно возвращает на обзор.

## 4. Что подтверждено запуском

Production-сборка запускалась как реальный сервер (`node dist/server.cjs`, `NODE_ENV=production`, SQLite в отдельном каталоге) и проверялась через HTTP:

* `GET /` → 200 `text/html`, SPA; `GET /assets/*.js` → 200; произвольный путь → SPA fallback 200; `GET /api/unknown` → JSON 404;
* `/api/health` и `/api/health/db` → 200;
* сценарий: регистрация владельца и ученика → вход → создание класса → вступление по коду → запрет создания события ученику (403) → создание события владельцем → фильтр событий по датам → некорректный фильтр (400) → CSRF с чужим `Origin` (403) → список участников → `PATCH max_members` → закрытие входа → logout → `/api/auth/me` после logout (401);
* cookie: `HttpOnly; SameSite=Lax`, `Secure` при `X-Forwarded-Proto: https`, отсутствие `Secure` при `TRUST_PROXY=0`;
* реальный TLS-прокси (аналог Nginx): HSTS, `Secure`-cookie, CSRF `Origin` и создание класса по HTTPS — проверены end-to-end;
* CI собрал production-образ на Node 24, запустил контейнер и проверил `/api/health/db`, отдачу SPA и сохранение `calendar_db.sqlite` на volume.

Каждая проверка печатается как `[PASS]`; итоговые строки прогона: `ALL 26 VERIFICATION CHECKS PASSED SUCCESSFULLY!` и `ALL 50 INSTALLER SIMULATION CHECKS PASSED`.

## 5. Остаточные риски и что сделать на реальном сервере

1. **Nginx и Certbot не запускались вживую** (в песочнице нет Docker/apt). Docker-образ собран и успешно запущен в CI, логика установщика проверена 50 сценариями симуляции, включая реальный диалог через pty. Финальный прогон нужен на реальном VPS:
   ```bash
   bash <(curl -Ls https://raw.githubusercontent.com/wisoqu/Interactive-calendar/<ветка-или-main>/install.sh)
   ```
   Ожидаемые точки контроля: `install.sh` дошёл до «✓ Установка успешно завершена», открывается `https://<домен>`, `curl -fsS https://<домен>/api/health/db` возвращает `healthy`.
2. **DNS/порты** — вне контроля установщика: A-запись должна указывать на сервер, а 80/443 открыты в панели провайдера.
3. **SMTP** — требует «пароля приложения»; без SMTP сброс пароля по почте недоступен (восстановления без email в приложении нет).
4. **Let's Encrypt rate limits** — если выпускать сертификаты многократно на одном домене, можно упереться в лимиты; для отладки используйте staging: `certbot --nginx --staging -d <домен>`.
5. **Публикация изменений** — установочная команда из README ссылается на ветку `main`. До слияния PR используйте `--ref <ветка>` или ссылку на raw-файл своей ветки.
