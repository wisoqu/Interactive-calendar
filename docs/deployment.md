# Deployment Guide - Interactive Calendar

This document describes the production container packaging, environment configuration, persistent SQLite volume mounting, HTTPS reverse proxy setup, upgrades and backups.

## 1. Environment Variables (`.env`)

For local development, copy `.env.example`:

```dotenv
NODE_ENV=development
PORT=3000
BIND_HOST=0.0.0.0
LISTEN_HOST=0.0.0.0
TRUST_PROXY=1
SQLITE_DB_PATH=./data/calendar_db.sqlite
```

Production values generated by `install.sh` for the Docker profile:

```dotenv
NODE_ENV=production
PORT=3000
# Host interface where Docker publishes the port:
#   0.0.0.0   -> app reachable directly on IP:3000 (no domain)
#   127.0.0.1 -> app reachable only through Nginx/HTTPS
BIND_HOST=127.0.0.1
# Address the Node process listens on inside the container (always 0.0.0.0 in Docker).
LISTEN_HOST=0.0.0.0
# Trust one reverse-proxy hop (Nginx). Set to 0 when the app is exposed directly.
TRUST_PROXY=1
SQLITE_DB_PATH=/app/data/calendar_db.sqlite

# Optional SMTP settings for 6-digit password reset emails
SMTP_HOST="smtp.gmail.com"
SMTP_PORT=587
SMTP_USER="your_account@gmail.com"
SMTP_PASS="your_16_char_app_password"
SMTP_FROM="Школьный календарь <your_account@gmail.com>"
SMTP_SECURE=false
```

### Environment variables reference

| Variable | Default | Purpose |
| :--- | :--- | :--- |
| `NODE_ENV` | `development` | `production` disables Vite middleware and serves `dist/` |
| `PORT` | `3000` | Port the Node process listens on and Docker publishes |
| `BIND_HOST` | `0.0.0.0` | Host interface for the Docker port mapping (Compose interpolation only) |
| `LISTEN_HOST` | `0.0.0.0` | Interface inside the Node process. Keep `0.0.0.0` in Docker |
| `TRUST_PROXY` | `1` | Trust `X-Forwarded-*` from one proxy hop. Use `0` for direct `IP:3000` |
| `SQLITE_DB_PATH` | `./data/calendar_db.sqlite` | Absolute path recommended in Docker (`/app/data/...`) |
| `SMTP_HOST` / `SMTP_USER` / `SMTP_PASS` | empty | Enable password-reset emails; all three are required |
| `SMTP_PORT` | `587` | `465` implies `SMTP_SECURE=true` |
| `SMTP_FROM` | localized brand | Sender address/name; placeholders with `@example.com` are replaced automatically |
| `SMTP_SECURE` | `false` | Implicit TLS (SMTPS) |
| `RATE_LIMIT_LOGIN_MAX` | `20` | Login attempts per `IP + username` per 15 min |
| `RATE_LIMIT_REGISTER_MAX` | `50` | Registrations per IP per hour |
| `RATE_LIMIT_RESET_REQUEST_MAX` | `5` | Reset requests per email per 15 min (plus 100/IP/15 min) |
| `RATE_LIMIT_RESET_CONFIRM_MAX` | `15` | Reset confirmations per email per 15 min |
| `RATE_LIMIT_JOIN_MAX` | `25` | Invite-code joins per authenticated user per 15 min |

## 2. Docker & Persistent SQLite Volume (`Dockerfile` + `docker-compose.yml`)

* **Multi-stage Alpine build (`Dockerfile`)**: installs dependencies cleanly with `npm ci`, compiles frontend static assets (`dist/`) and the Node server bundle (`dist/server.cjs`), then runs `npm prune --omit=dev` so production images contain only runtime dependencies (`better-sqlite3`, `dotenv`, `express`, `nodemailer`).
* **Non-root execution (`docker-entrypoint.sh`)**: ensures `/app/data` is owned by `node:node` on container boot and drops privileges via `su-exec node` so the Node.js application never runs as `root`.
* **WAL-safe directory mount (`docker-compose.yml`)**: SQLite in `WAL` mode creates companion `-wal` and `-shm` files alongside `calendar_db.sqlite`, so `./data` is mounted as a directory to `/app/data`. The image's `healthcheck` monitors `/api/health`.
* **Operational defaults**: `init: true` (tini forwards signals), `stop_grace_period: 15s`, and JSON log rotation (`10 MB × 3`) so a small VPS disk cannot fill up with logs.

```yaml
services:
  app:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: school_calendar_app
    restart: unless-stopped
    init: true
    stop_grace_period: 15s
    ports:
      - "${BIND_HOST:-0.0.0.0}:${PORT:-3000}:${PORT:-3000}"
    env_file:
      - .env
    environment:
      - NODE_ENV=production
      - SQLITE_DB_PATH=/app/data/calendar_db.sqlite
      - LISTEN_HOST=0.0.0.0
    volumes:
      - ./data:/app/data
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

> **Important:** never point `LISTEN_HOST` at `127.0.0.1` inside Docker. The published host port is forwarded to the container's bridge interface, so a loopback-only Node process would be unreachable. Use `BIND_HOST=127.0.0.1` on the host side instead.

## 3. One-Command Automated Setup (`install.sh`)

On Ubuntu/Debian servers, `install.sh` automates:

1. Checking available RAM and optionally provisioning a 2 GB `/swapfile` on low-memory VPS instances.
2. Non-interactively installing `git`, `curl`, `docker`, and the Docker Compose plugin (with retries for temporary `apt` locks).
3. Cloning or safely updating the repository into `/opt/interactive-calendar` and generating a properly escaped `.env` (mode `600`).
4. Asking explicitly whether to configure SMTP (`[y/N]`, default **no**) and collecting the mail settings only on request.
5. Building and starting the container via Docker Compose, polling `/api/health/db` for up to 90 seconds, and printing container logs on failure.
6. Asking explicitly whether to attach a domain (`[y/N]`, default **no**). On `y`: validating DNS, installing Nginx + Certbot (apt is invoked with `DPkg::Lock::Timeout=300` and retried, so a concurrent `unattended-upgrades` run does not abort the installation), requesting the `Let's Encrypt` certificate immediately, switching `BIND_HOST=127.0.0.1` / `TRUST_PROXY=1`, and verifying `Nginx → Node` locally (`curl --resolve … https://<domain>/api/health`). Existing HTTPS settings are detected and reused on re-runs.

Prompts are printed to the same stream as the rest of the installer output (and the log), while answers are read from `/dev/tty`, so questions never interleave with Docker build output. Without a TTY the installer requires `--yes`.

### Interactive and non-interactive usage

```bash
# Dialog mode (install dir, SMTP? [y/N], domain? [y/N], then domain + Let's Encrypt email)
bash <(curl -Ls https://raw.githubusercontent.com/wisoqu/Interactive-calendar/main/install.sh)

# Fully non-interactive
bash install.sh --yes --no-swap \
  --dir /opt/interactive-calendar \
  --domain calendar.school42.ru --email admin@school42.ru
```

`bash install.sh --help` lists all flags: `--dir`, `--domain`, `--email`, `--port`, `--ref`, `--no-ssl`, `--no-swap`, `--reconfigure-env`, `--smtp-host`, `--smtp-port`, `--smtp-user`, `--smtp-pass`, `--smtp-from`.

On failure the installer prints the failed command, the installation log path (`/var/log/interactive-calendar-install.log`), container log commands and `git status`.

### Prerequisites for HTTPS

* The domain's **A record** must already point to the server's public IPv4 address.
* Ports **80 and 443** must be open in the cloud provider firewall *and* the OS firewall (`ufw`/`firewalld`). The installer opens `Nginx Full` when `ufw` is active and `http`/`https` when `firewalld` is active, but cloud security groups must be changed in the provider panel.
* If DNS is still propagating, the installer retries Certbot once and prints the exact `certbot --nginx -d <domain>` command for a later manual attempt.

## 4. Upgrades, Backups and Restore

```bash
# Upgrade code + rebuild container (keeps .env, SQLite and HTTPS settings)
bash /opt/interactive-calendar/install.sh --yes

# Consistent backup: stops the container for a second, archives data/ and .env, restarts
bash /opt/interactive-calendar/backup.sh
# Manual equivalent:
#   cd /opt/interactive-calendar && docker compose stop
#   tar czf ~/calendar-backup-$(date +%F).tgz data .env
#   docker compose start

# Restore
tar xzf ~/calendar-backup-YYYY-MM-DD.tgz -C /opt/interactive-calendar
cd /opt/interactive-calendar && docker compose restart
```

Changing SMTP after installation:

```bash
nano /opt/interactive-calendar/.env
cd /opt/interactive-calendar && docker compose up -d
```

## 5. Manual Docker Deployment (without `install.sh`)

```bash
git clone https://github.com/wisoqu/Interactive-calendar.git
cd Interactive-calendar
cp .env.example .env
# edit NODE_ENV=production, BIND_HOST and SMTP_* as needed
mkdir -p data
docker compose up -d --build
curl -fsS http://127.0.0.1:3000/api/health/db
```

Then configure Nginx/Certbot manually as described in `README.md` (section “Ручная настройка HTTPS”), remembering `BIND_HOST=127.0.0.1` and `TRUST_PROXY=1`.

## 6. Verification and CI

Local checks (no server required):

```bash
npm ci
npm run lint          # strict TypeScript
npm test              # 26 integration/unit checks
npm run test:install  # 80 installer checks (no network, mocked docker/nginx/certbot, interactive pty, backup)
npm run check         # all of the above + production build
```

Docker image in CI (`.github/workflows/ci.yml`): builds the production image, runs it with a host-mounted `./ci-data` volume, waits for `/api/health/db`, verifies the SPA HTML and the persisted SQLite file, then prints container logs.

## 7. Troubleshooting

| Symptom | Checks |
| :--- | :--- |
| Container exits immediately | `docker compose logs --tail=200`; `df -h`; permissions on `./data` |
| `502 Bad Gateway` from Nginx | `docker compose ps`; app port vs `proxy_pass` in `/etc/nginx/sites-available/interactive-calendar`; `TRUST_PROXY=1` |
| Certificate not issued | DNS A record; ports 80/443; no other web server on port 80; `sudo certbot --nginx -d <domain>` |
| `429 RATE_LIMITED` for a whole class | Raise `RATE_LIMIT_*_MAX` in `.env`, then `docker compose up -d` |
| Password reset emails missing | SMTP credentials (app password), `[SMTP ERROR]` in logs, spam folder |
| `Secure` cookie missing | HTTPS profile must have `TRUST_PROXY=1` and Nginx must send `X-Forwarded-Proto: https` |
